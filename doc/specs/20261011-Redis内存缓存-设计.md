# Redis 内存缓存：设计

状态：已按确认方案实施，2026-10-12 复核。创建日期：2026-10-11，保持首次创建日期。

## 目标、范围与事实

请求优先读取进程内缓存；未命中时读取 Redis 并回填；每五分钟从 Redis 刷新已缓存的数据。
Redis 是配置事实来源，内存只是只读副本，不自动写入 Redis，不缓存 Mongo 查询结果。
`REDIS_CACHE_ENABLED` 默认 true。false 时三类读取都绕过内存和合并读取，每请求直接读 Redis，
不回填、不启动后台刷新，手动 Refresh 也不读取数据源。修改后重启生效，不支持运行时热切换。
关闭时保持 JSON、状态/到期和错误码校验；没有旧快照兜底，Redis 故障直接返回服务异常。
直读仍保留回源并发限制、超时、请求取消及关闭保护；其他缓存配置仍校验为合法正值。
读取策略封装为独立的数据读取层，当前顺序为内存 → Redis；未来可配置为内存 → Redis → MySQL。
MySQL 尚未接入，本设计只确定扩展边界，不创建连接、表或依赖。

事实来源：pkg/redis/apikey_store.go、product_auth.go、product_map.go、
app/auth/credential.go、app/middleware/loan_auth.go、bootstrap/route.go。
实施前凭据和 mongo_map 每请求读取 Redis；产品授权原工作区实现按缓存年龄回源且无容量上限。
本轮已替换为 app/configdata 三类统一读取，刷新由 bootstrap 显式启动和关闭，Redis 构造函数不启动 worker。

本轮范围：“apikey product 信息”覆盖下列三类数据，按需加载，不扫描 Redis 全库。

| 数据 | Redis 来源 | 内存键 | 内存值 |
| --- | --- | --- | --- |
| API Key 凭据 | String gin-finapi:auth:apikey:v1:<摘要> | API Key SHA-256 摘要 | version、secret、status、expires_at |
| API Key 产品授权 | String gin-finapi:auth:apikey-product:v1:<摘要>:<pcode> | 摘要+pcode | version、status、expires_at |
| 产品变量映射 | String gin-finapi:product-map:v1:<pcode> | pcode | 变量名到 CSV 下标的映射 |

保持凭据/授权 Redis Key 与 JSON、签名算法、Mongo t/v 和 gzip/CSV 格式；仅产品映射 Key 从 Hash 转为 String KV。
映射 JSON 不变，迁移显式执行，见发布章节。缓存策略不新增产品业务规则。
产品授权是否启用由既有授权链路决定，不以开启缓存作为启用授权的开关。

## 数据读取层与职责

HTTP 中间件和查询用例只调用有类型的读取方法，不判断数据来自内存、Redis 还是 MySQL：

```go
type Reader interface {
    LoadCredential(ctx context.Context, apiKey string) (auth.Credential, error)
    LoadProductAccess(ctx context.Context, apiKey string, pcode int) (auth.ProductAccess, error)
    LoadProductMap(ctx context.Context, pcode int) (map[string]int, error)
}
```

当前 Reader 为具体类型，公开上述方法以及 CheckProductAccess；消费者注入单个方法，不依赖完整接口。
app/configdata 同包组织 reader.go（读取顺序）、cache.go（内存）、refresh.go（刷新），
其依赖指向业务类型和配置类型，不引用 Redis。pkg/redis 提供适配器，bootstrap 注入并管理生命周期。
未来 pkg/mysql 适配器实现同一读取边界，业务调用方无需改动；实际名称和文件以实施时最小拆分为准。

读取层负责逐层查找、并发回源合并、内存回填及同步发布。适配器负责 GET（迁移工具使用 HGET）或未来 SQL、
数据格式解析、超时及错误分类。认证层负责 status、expires_at、签名和权限判断，
HTTP 错误转换仍放在现有适配边界。低优先级数据源不能覆盖高优先级数据源的明确拒绝状态。

数据源内部约定分别表达“找到记录”“没有记录”和“读取失败”，例如：

```go
type Source[K comparable, V any] func(ctx context.Context, key K) (value V, found bool, err error)
```

三类读取复用泛型缓存和 Source 函数；不建立通用 CRUD 框架。
不同类型保留各自解析和错误转换，连接串、Redis Key/SQL 细节不进入 HTTP 或业务层。

| 本层结果 | 读取层动作 |
| --- | --- |
| 找到有效格式的记录 | 返回并回填内存，结束读取链 |
| 找到禁用或已到期记录 | 返回该记录，由认证层拒绝；不继续查低层 |
| 没有记录 | 继续下一已配置数据源；全部缺失才转为对应业务错误 |
| 网络/超时/权限故障或记录格式损坏 | 返回对应错误，不默认降级到低层 |

当前仅配置 Redis，Redis 缺失即最终缺失。未来 MySQL 接入后的故障降级必须单独确认，
不能把任意 error 当作缓存未命中。尤其 Redis 删除记录后若 MySQL 仍有旧记录，可能重新启用授权；
接入时必须定义 MySQL 是否为权威源、删除/禁用如何同步及是否需要明确的撤销记录。
当前成功读取只回填内存；从 MySQL 回填 Redis 属于后续写入策略，不能随读取层自动启用。

## 请求读取

1. 查询对应类型的缓存。
2. 命中：使用当前快照，不检查缓存是否达到五分钟；凭据/授权仍逐次检查 status 和 expires_at。
3. 未命中：读取层调用 Redis 适配器精确 GET。合并读取使用读取器生命周期 Context 和 REDIS_TIMEOUT；每个等待者独立响应自身请求取消，首个请求取消不影响其他等待者。
4. 后续启用 MySQL 时，仅 Redis 明确缺失才继续 MySQL；当前没有该层。读取成功且内容通过原有校验后，原子替换内存缓存，再按既有业务流程处理。
5. Redis 明确不存在或数据无效：移除旧快照；禁用记录缓存为拒绝状态，执行对应错误处理。
6. 未命中时 Redis 故障：返回既有服务异常，不缓存失败结果。

ExpiresAt 是业务到期时间，五分钟仅是后台同步周期，不是缓存 TTL。
例如授权在一分钟后到期，即使后台尚未同步，到期后也必须拒绝。
失效的凭据不会因缓存命中而绕过签名、时间戳或产品授权校验。

## 五分钟同步

首期推荐按需加载，并刷新已访问项；启动时缓存为空，请求缺失时即时读取 Redis。
每五分钟复制各缓存的键列表，分批精确读取 Redis，校验后逐条替换、失效或删除。
同步通过读取层的 Refresh 路径执行，该路径跳过内存，从当前持久化数据源链重新读取；
不能调用默认 Load 后误把内存旧值重新写回内存。未来新增 MySQL 后，刷新也使用同一已配置源链及缺失/错误规则。
刷新期间读缓存不被整批网络操作阻塞。新增条目不用等待下一轮同步；本轮未覆盖的新增条目
依靠请求回填及下一轮同步，请求不依据缓存年龄触发额外回源。

不要求三类数据构成跨 Key 原子快照。凭据、授权和映射分别发布，保持当前跨 Redis Key
读取的兼容边界。若后续要求统一版本，应另外设计版本字段及发布协议。

后台同步发生网络、超时或 Redis 权限故障时，保留上一份已验证快照，记录失败并等待下一周期。
Redis 明确返回删除、禁用或无效内容时，必须移除旧有效快照或替换为明确的拒绝状态，不能当作网络故障继续放行。
同步正常时，禁用、删除、secret 轮换及映射变更通常在下一轮同步完成后生效，窗口约为五分钟加同步耗时；已经开始的请求可能完成。
同步持续失败时，旧快照会继续使用，远端撤销或轮换的传播延迟没有五分钟硬上限；本地 expires_at 校验仍生效。
需要立即撤销的运营要求与本策略不兼容，应另行设计主动失效通知。

同步结果记录固定 checked、failed、duration_ms；失败用 Warn，成功用 Debug，不记录 API Key、摘要、secret、JSON 或驱动原始错误。
不把 KEY、pcode 或客户标识用作高基数指标标签，不宣称已经接入指标平台。

备选：全量预加载全部 Redis 配置。需要授权条目数量、扫描索引、批大小和内存预算后才能选择；
当前没有账号或产品授权列表索引，不能直接用 KEYS 或无上限 HGETALL 实现。

## 并发、容量与资源所有权

- 缓存实例由 bootstrap 装配，业务/HTTP 层仍通过注入的读取函数访问。
- 使用三个有类型的缓存，分别复用已有解析器；不把业务错误转为字符串后再判断。
- 热路径只短暂持有缓存锁以维护 LRU。Redis I/O 不持有全局缓存锁；同一个键的并发回源合并，不同键独立读取。
- 请求等待合并读取时仍响应自己的 Context 取消，不能因后台刷新等待无限阻塞。
- 后台与请求可能同时回源，按键串行或使用条目版本，避免较旧读取覆盖新快照。
- 产品映射返回副本或使用明确的不可变边界，调用方不得修改共享 map。
- 每类缓存有独立最大条目数；达到上限时淘汰最久未使用项，不能绕过 Redis 校验。
- 按容量淘汰长期未访问项，不按五分钟缓存年龄删除；不缓存随机未知 API Key/授权组合，避免无限积累。
- 同步并发和批大小有上限；不持有大批副本，不为每个条目创建长期 goroutine。
- 刷新 worker 由 bootstrap 启动和停止；读取器构造函数不隐式启动后台任务。
- 关闭顺序：HTTP 排空 → 取消并等待刷新 worker → Mongo/Redis 关闭；后台读使用可取消 Context。

建议使用标准库完成锁、定时器和生命周期管理；若复用已有并发工具，先核对锁定版本，
不为缓存新增依赖。保留当前认证和产品映射 Redis 池所有权，不在本变更中合池。

## 配置建议

以下参数已实现；默认容量和并发仅为初始保护值，不是生产容量结论，需按实际规模调整。

| 建议参数 | 建议值/要求 | 职责 |
| --- | --- | --- |
| REDIS_CACHE_REFRESH_INTERVAL | 5m，必须为正时长 | 仅控制后台同步周期 |
| REDIS_CACHE_ENABLED | 默认 true，合法布尔值 | false 关闭三类缓存及刷新，逐请求直读 |
| REDIS_APIKEY_CACHE_MAX_ENTRIES | 默认 1000，正整数 | 凭据容量 |
| REDIS_PRODUCT_AUTH_CACHE_MAX_ENTRIES | 默认 10000，正整数 | 授权容量 |
| REDIS_PRODUCT_MAP_CACHE_MAX_ENTRIES | 默认 1000，正整数 | 映射容量 |
| REDIS_CACHE_SYNC_CONCURRENCY | 默认 4，正整数，三类读取共用 | 请求及刷新回源并发上限 |

沿用 REDIS_TIMEOUT 约束单条回源和冷读取的排队/合并等待；缓存命中不创建超时计时器。
缓存数据量和刷新并发不能直接等同 Redis 连接池大小。
配置解析与验证放 pkg/config，不让 Handler 或缓存实现反复读取环境变量。

## 错误与兼容

| 情形 | 现有 HTTP/业务码 |
| --- | --- |
| API Key 缺失、禁用或到期 | 400/2001 |
| API Key 产品授权缺失、禁用或到期 | 403/2004，依现有授权链路 |
| 产品映射缺失或格式无效 | 200/6001 |
| Redis 故障、损坏凭据或授权记录 | 503/9002 |

缓存命中无需访问 Redis，也不检查缓存年龄；同步失败时已有快照仍可使用。
未命中时读取 Redis，按上表返回错误。后台明确发现记录失效时，不能保留旧的有效快照。
secret 会存在进程内存，禁止持久化、输出或用于日志；每请求仍用当前快照验证签名。

## 实施顺序与验收

1. 确定数据源接口及缺失/拒绝/故障语义；封装内存 → Redis 读取层，明确容量和刷新并发配置。
2. 将 API Key 凭据读取接入该层，保留严格 JSON 校验和逐次到期检查。
3. 缓存产品授权，移出当前构造函数内的定时 worker，并补按键并发控制和容量管理。
4. 缓存产品映射 KV，保证映射副本不会被调用方修改，并提供显式迁移 CLI。
5. 在 bootstrap 统一装配和停止刷新 worker，同步现有文档和回归资产。

使用 Go testing、fake Redis 边界和 httptest；不访问生产 Redis。验收至少覆盖：
首次回源、缓存超过五分钟仍命中且不回源、后台周期刷新、业务提前到期、secret 轮换、授权撤销、映射修改/删除、
同步故障保留快照、明确失效清除快照、同键合并/不同键隔离、旧读取不覆盖新值、容量淘汰、map 隔离和退出取消。
用 fake 后续数据源验证：高层命中不读低层、仅缺失继续、禁用不继续、故障不继续，刷新确实跳过内存。

实施后执行 go test -race ./...、go vet ./...、go build ./...、go mod verify、git diff --check。
Go 使用 1.24.0/toolchain go1.24.10，中文注释、gofmt，同包测试；不得以删测试或降校验通过门禁。
实施测试覆盖上述读取、取消、刷新、容量、拒绝和 map 隔离边界；后续真实 Redis 集成及容量评估需要隔离环境。

## 发布、回滚与待确认

发布前准备有效 Redis 凭据、授权和映射；每个服务进程拥有独立缓存，没有跨进程共享内存。
发布前核对所有有效 pcode，获得目标 Redis/DB 写入授权后，逐产品执行：

```bash
go run cmd/init_redis.go -pcode 10001 -migrate-map
```

工具读取旧 Hash、复用格式校验、SET NX 新 String；不删除源、不覆盖目标，不自动处理全部产品。
旧 Hash 缺失/无效或写入失败返回非零；已有目标须人工核对内容和 TTL，不能把“保留”当作验证通过。
应用不自动迁移，也不回退旧 Hash。源正在变更时需协调暂停更新，迁移不是跨键事务。
回滚旧二进制继续读取保留的 Hash；切换后的 KV 更新须同步旧 Hash 才能无损回滚。
回滚缓存不能取消产品授权校验。未经明确要求不提交、推送、部署或执行初始化。

已确认：缓存命中时不检查是否达到五分钟，五分钟仅作为后台同步周期。
已确认：统一封装数据读取，内存为第一层、Redis 为第二层，保留后续 MySQL 接入边界。
已实施：覆盖三类数据，按需加载并刷新缓存项；移除按 syncedAt 判断五分钟后回源的逻辑。
待确认：生产数据规模、内存预算、立即撤销需求、隔离 Redis 集成和实际迁移验收。

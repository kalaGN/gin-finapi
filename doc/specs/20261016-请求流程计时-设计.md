# 请求流程计时：设计

## 目标与已确认方案

用户已确认将请求日志duration_ms从整数改为JSON对象，记录相对入口的累计毫秒数，
并提供基于context.Context的公共方法供后续节点复用；不新增目录或依赖。
事实来源：app/middleware/logger.go、loan_auth.go、app/services/product_query.go、pkg/logger/request_log.go。
需要回答：耗时发生在鉴权、映射还是查询？失败请求执行到了哪里？整个请求何时完成？

## 格式与边界

```json
{"duration_ms":{"entry":0,"auth":3,"product_map":4,"query":12,"finish":13}}
```

- entry固定0；其余为单调时钟计算的累计整数毫秒，不是各阶段独立耗时，不保证JSON字段顺序。
- Logger中间件入口启动计时，包含请求体采集、限流、SID与业务链；不代表TCP接收时刻。
- auth在参数校验、凭据、签名、产品授权结束时记录，失败也记录；必须在c.Next之前，不能包含业务处理。
  auth表示鉴权链退出而非认证通过；异常退出也由defer记录，同名首次规则避免成功后的defer覆盖。
- product_map在映射读取返回时记录（含失败）；query在实际数据查询返回时记录（含失败）。
  映射/查询Panic未正常返回时不伪造完成节点；外层Recovery后仍有finish。未执行阶段不补0。
- finish为业务链返回后、日志整理/格式化/排队之前的时间点；不包含异步文件/Redis写入耗时。
- /health和其他非业务请求仅有entry/finish；限流短路无auth；管理鉴权不冒用/api的auth节点。
- 仅修改请求完成日志；缓存刷新、MySQL同步等后台日志duration_ms保持整数。
- HTTP响应、计费success/charge、SID、完整Body/响应及异步队列/重试行为均保持不变。
  不新增敏感字段、不使用用户输入作为节点名、不接监控平台或报警。

## 公共方法与实现顺序

1. pkg/utils/timing.go及同包测试：StartTiming(ctx)、MarkTiming(ctx,name)、TimingSnapshot(ctx)。
   私有Context key和每实例mutex，无全局请求状态；重复Start保留原起点；节点同名取首次，
   空名/entry保留名不覆盖；无计时器时Mark为空操作、Snapshot返回nil。
   Snapshot深拷贝map；并发标记/读取安全，不暴露活动map给异步日志。
2. Logger创建Context，结束标记finish并输出快照；计时不改变Context取消、截止或已有值。
3. LoanAuth在所有返回路径记录auth；成功在c.Next之前记录；Service记录映射/查询，保持原返回错误。
4. 同步README、Rules及索引。注释中文、gofmt；不移动已有文件、不修改main。

调用示例：

```go
ctx = utils.StartTiming(ctx)
utils.MarkTiming(ctx, "auth")
points := utils.TimingSnapshot(ctx)
```

## 兼容、风险与回滚

duration_ms类型变化为已批准日志契约变更，外部消费端需适配，仓库不能证明外部消费者已升级。
毫秒以下节点可能相同；新增节点需固定名称、有限基数，不能将API Key/手机号/SID作为键。
计时器只存当前请求节点，不缓存请求内容；Snapshot不包含后续后台标记。
回滚本次代码/文档即可，无数据迁移；不得自动Commit、Push或部署。

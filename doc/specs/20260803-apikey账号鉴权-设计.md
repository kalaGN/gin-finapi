# API Key 账号鉴权：设计

> 状态：历史草案，尚未实施。
>
> 2026-10-11 用户选择先用配置 API_KEY + SECRET_KEY，并将鉴权迁入中间件；
> 当前实现以 [请求加密鉴权需求](20261011-请求加密鉴权-需求.md) 为准。
> 下文每账号 secret 与多级缓存描述保留为历史决策背景，不代表当前服务能力。

## 目标与可测试验收标准

为 `POST /loan` 增加真实的 API Key 账号鉴权，在查询贷款数据前保证：

1. `apikey` 在账号存储中存在。
2. 该账号的 `status` 严格等于 `1`。
3. 使用该账号独立的 `secret` 验证请求签名。

可观察的验收标准：

- 已存在且 `status=1` 的 API Key 通过鉴权，继续现有时间戳、签名和贷款数据查询流程。
- API Key 不存在或对应账号 `status!=1` 时，终止请求，不查询贷款数据。
- API Key 不存在、账号禁用或签名错误等鉴权拒绝统一返回 HTTP `200`，通过 JSON `status` 业务码区分原因。
- 运营中心超时、不可用或返回无法校验的账号数据，且本地没有 60 秒内的新鲜记录时，
  返回 HTTP `503` + `ErrServiceUnavailable (9002)`。
- 账号在运营中心禁用后，最迟 60 秒内对所有 Airis 实例生效；正常的主动缓存失效应使其更快生效。
- 对外不区分“Key 不存在”和“账号被禁用”，避免泄露账号状态。
- `GET /health` 不受鉴权影响。
- 请求体字段、签名参数和签名算法不变。

## 当前实现与问题

- `app/Http/controllers/loan/index.go` 只校验 `apikey` 非空，随后将其纳入现有签名计算。
- 当前验签使用环境变量 `SECRET_KEY` 中的全局共享 secret，并没有实现每账号独立 secret。
- 已确认现有客户端使用每账号独立 secret，不使用服务端全局 `SECRET_KEY`。因此当前代码与真实客户端契约冲突，
  本方案需要修正服务端验签密钥来源，客户端不做 secret 迁移。
- 已确认账号权威数据来自运营中心接口，响应包含可直接用于验签的明文 secret。
- `app/middleware/auth.go` 的 `APIKeyAuth` 只读取 Query/Header，且没有挂载到 `/loan`；而当前公开契约中 `apikey`
  位于 JSON 请求体。
- 已启用的 MongoDB 是当前唯一持久化主调用链依赖；Redis 代码虽存在，但尚未启用；仓库中没有 MySQL
  配置、客户端或驱动依赖。
- 现有 `pkg/redis` 用 `context.Background()` 且将“Key 不存在”和“Redis 故障”都转成空值，不能直接用于需要
  明确降级语义的鉴权链路。
- 当前日志会记录完整请求体，其中包含 `phone`、`apikey` 和 `sign`。在鉴权上线前必须同步停止记录这些敏感原值。

## 方案及备选方案

### 推荐方案：三层本地存储 + 运营中心权威源

运营中心接口是账号权威数据源。MySQL 是本地持久化缓存，Redis 是跨实例二级缓存，每个 Airis 进程
保有容量受限的一级内存缓存。增加统一 `AccountStore` 边界，由 Loan Handler 在 JSON 绑定和基础参数校验后调用：

```text
POST /loan
  -> 绑定 JSON，校验必填项/类型/时间戳
  -> 对 apikey 做 SHA-256，仅作为缓存 Key
  -> L1 进程内存：命中则返回账号与明文 secret；未命中/过期/内部异常则读 L2
  -> L2 Redis：命中则回填 L1 并返回；未命中/异常则读 L3
  -> L3 MySQL：命中且 refreshed_at 不超过 60s 则回填 Redis/内存并返回
  -> MySQL 未命中/过期/异常：调用运营中心批量账号接口
  -> 运营中心返回完整批次：先全量校验，再批量回填 MySQL，并将目标账号回填 Redis -> 内存
  -> 目标 apikey 不在已验证的完整批次中：拒绝并缓存短期负结果
  -> 运营中心故障且无新鲜本地记录：HTTP 503 并 fail closed
  -> status != 1：拒绝
  -> 使用账号明文 secret 验证现有请求签名
  -> 查询贷款数据并返回
```

不直接在现有 Gin 中间件中解析 JSON，避免重复读取/恢复 Body、重复 DTO 和改变现有请求契约。
账号查询通过小接口注入 Handler，以便用内存 fake 做 `httptest` 组件测试，不让组件测试依赖真实 Redis/MySQL。

“一层失败读下一层”中的失败仅指缓存未命中、过期、解析失败或依赖异常。已命中的 `status!=1` 是有效鉴权结果，
应立即拒绝，不得为寻找可能的启用值而继续向下查询。

### 备选方案

| 方案 | 不采用原因 |
| --- | --- |
| 将 API Key 改为 `X-API-Key` Header 并复用现有中间件 | 会改变已有 JSON 和签名契约，需客户端迁移 |
| 配置文件/环境变量静态白名单 | 状态变更需重启，账号增多后不易管理，也不适合审计 |
| 只保存 `secret` 的单向哈希 | 现有签名算法验签必须取得原始 secret，单向哈希无法直接参与验签 |

## 数据模型与迁移

### MySQL 表（本地持久化缓存）

```sql
CREATE TABLE accounts (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    account_id VARCHAR(64) NOT NULL,
    name VARCHAR(128) NOT NULL,
    apikey VARCHAR(64) NOT NULL,
    secret VARBINARY(256) NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    refreshed_at DATETIME(3) NOT NULL,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_accounts_account_id (account_id),
    UNIQUE KEY uk_accounts_apikey (apikey)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 推荐 MySQL 环境变量

不推荐将用户名、密码和数据库名合并到一个 `MYSQL_DSN`。推荐由程序读取下列独立配置，
校验后仅在内存中构造驱动 DSN：

```dotenv
# 必填连接信息
MYSQL_HOST=mysql.internal.example
MYSQL_PORT=3306
MYSQL_DATABASE=airis
MYSQL_USER=airis_auth
MYSQL_PASSWORD=<injected-secret>

# 生产环境必须验证服务端证书；私有 CA 时提供后两项
MYSQL_TLS_MODE=verify-full
MYSQL_TLS_CA_FILE=/etc/airis/certs/mysql-ca.pem
MYSQL_TLS_SERVER_NAME=mysql.internal.example

# 超时初始值
MYSQL_CONNECT_TIMEOUT=1s
MYSQL_QUERY_TIMEOUT=500ms
MYSQL_WRITE_TIMEOUT=2s

# 连接池初始值，上线后按单实例 QPS 和 MySQL 连接配额调整
MYSQL_MAX_OPEN_CONNS=20
MYSQL_MAX_IDLE_CONNS=10
MYSQL_CONN_MAX_LIFETIME=30m
MYSQL_CONN_MAX_IDLE_TIME=5m
```

本地开发 `.env` 已于 2026-08-03 按上述变量名完成占位配置，其中 `MYSQL_HOST=127.0.0.1`、
`MYSQL_DATABASE=airis`、`MYSQL_USER=airis_auth`、`MYSQL_TLS_MODE=disabled`，密码仍为待替换的本地占位值。
该文件已被 Git 忽略，不得因此将真实密码同步到 `.env.example` 或仓库。

上述本地 `.env` 只是实施前配置准备；当前 `pkg/config/app_config.go` 尚未解析这些 MySQL
变量，因此不代表 MySQL 账号存储已启用。本地联调前必须替换密码占位值；生产配置不得继承
`MYSQL_TLS_MODE=disabled`。

配置语义：

- `MYSQL_HOST`、`MYSQL_DATABASE`、`MYSQL_USER`、`MYSQL_PASSWORD` 在启用鉴权时必填；
  `MYSQL_PORT` 默认 `3306`，但非整数或超出 `1..65535` 必须拒绝启动。
- `MYSQL_DATABASE` 推荐使用独立库 `airis`；`MYSQL_USER` 推荐使用专用账号 `airis_auth`，
  只授予该库 `accounts` 表所需的 `SELECT/INSERT/UPDATE` 权限，不授予 `DROP/ALTER/GRANT`。
- `MYSQL_TLS_MODE` 生产环境只允许 `verify-full`；`disabled` 仅允许显式的本地隔离测试。
  使用私有 CA 时 `MYSQL_TLS_CA_FILE` 和 `MYSQL_TLS_SERVER_NAME` 必填，证书文件不进入仓库。
- `MYSQL_QUERY_TIMEOUT` 用于单个 `apikey` 索引查询；`MYSQL_WRITE_TIMEOUT` 用于批量快照 upsert。
  上述值是首期起点，不是已验证的性能 SLA。
- 连接池必须满足 `MAX_IDLE_CONNS <= MAX_OPEN_CONNS`，时长和整数解析失败时拒绝启动。
- 程序构造 DSN 时固定 `charset=utf8mb4`、`parseTime=true`、`loc=UTC`，不将 DSN、密码
  或包含凭据的驱动错误输出到日志或 HTTP 响应。

- `account_id`：稳定账号标识，不使用手机号或 API Key。
- `apikey`：客户账号的凭据标识，可明文存储并建立唯一索引；仍按敏感标识处理，不记录到日志。
- `secret`：运营中心返回的每账号独立明文 secret，可直接用于现有签名验证。因现有签名算法需要原 secret，
  该字段不能改为单向哈希。写入边界必须拒绝空值和超过 256 字节的值，不得截断。
- `status`：严格使用整数；`1` 表示启用，其他值包括缺失均视为不可用。首期不扩展角色或接口级权限。
- `refreshed_at`：Airis 最后一次从运营中心成功拉取该账号的 UTC 时间；超过 60 秒的记录不得直接用于鉴权。
- `created_at`/`updated_at`：UTC 时间，用于追踪变更；不作为首期鉴权条件。

鉴权 SQL 必须使用参数化查询并通过 `apikey` 唯一索引命中单行：

```sql
SELECT account_id, secret, status, refreshed_at, updated_at
FROM accounts
WHERE apikey = ?
LIMIT 1;
```

不把 `status` 合并到 SQL 条件，以便内部能区分“未知 Key”与“已禁用账号”；对外响应仍完全相同。

### Redis 和内存缓存

- Redis Key：`airis:auth:account:<sha256(apikey)>`，Value 包含 `account_id`、明文 secret、`status`、`refreshed_at`、
  `updated_at` 和缓存格式版本，不在 Redis Key 中包含明文 `apikey`。
- 内存 Key 使用同一 `sha256(apikey)`，条目包含账号快照、明文 secret 和过期时间。实现必须并发安全且设置硬容量上限，
  防止随机 Key 攻击耗尽内存。
- 首期值：L1 正向 TTL `10s`，Redis 正向 TTL 最大 `60s`，负结果 TTL `5s`。为避免集中过期，TTL 可做只会缩短的随机抖动，
  任何正向缓存的实际 TTL 都不得超过 60 秒禁用生效 SLA。
- 运营中心拉取成功后，按 MySQL -> Redis -> 内存回填；回填失败不改变本次已获得的账号鉴权结果，
  但必须记录分类错误。
- 只有目标 `apikey` 不在运营中心返回且已整批验证的完整账号快照中时，才缓存短 TTL
  负结果；MySQL 未命中、部分批次或非法响应都不能证明账号不存在。

上线前应提供可审查、非破坏性的 MySQL DDL。账号数据由 Airis 在请求路径从运营中心拉取并 upsert，
不由人工脚本创建权威账号。

### 运营中心与职责边界

- API Key/secret 的生成、客户交付、轮换和找回策略不属于 Airis 范围，权威数据由运营中心管理。
- Airis 调用运营中心批量账号接口，获取包含明文 secret 的完整账号快照，并对批次完整性、唯一性及
  每条记录的字段存在性、类型、长度和状态值做严格校验。
- 运营中心通过受控内网和 TLS 提供服务；认证凭据只由运行环境注入，不写入仓库或日志。
- Airis 不提供 secret 展示、导出或找回接口。

#### 运营中心账号查询 Mock 接口

真实运营中心契约尚未提供。首期联调先使用下列 Mock 契约；它是独立测试服务，不得注册到 Airis
`routes/api.go` 或暴露为 Airis 对外管理接口。

```http
GET /mock/operation-center/v1/accounts HTTP/1.1
Authorization: Bearer <mock-service-token>
X-Request-ID: <optional-correlation-id>
```

请求约束：

- 该 Mock 不接收 `apikey`、分页或过滤参数，每次返回一个完整账号快照。
- `Authorization` 只是 Mock 服务的最小访问保护，token 使用显式测试占位值并由环境注入；
  不预设真实运营中心的最终认证方式。
- `X-Request-ID` 可选；传入时 Mock 原样回传，未传入时由 Mock 生成不含账号信息的值。

查询成功时返回 HTTP `200`：

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "oc-mock-request-001",
  "data": {
    "snapshot_id": "mock-snapshot-001",
    "generated_at": "2026-08-03T08:00:00.000Z",
    "complete": true,
    "total": 2,
    "accounts": [
      {
        "account_id": "mock-account-001",
        "name": "mock-enabled-account",
        "apikey": "mock_enabled_key",
        "secret": "mock-secret-enabled-001",
        "status": 1,
        "updated_at": "2026-08-03T07:59:00.000Z"
      },
      {
        "account_id": "mock-account-002",
        "name": "mock-disabled-account",
        "apikey": "mock_disabled_key",
        "secret": "mock-secret-disabled-002",
        "status": 0,
        "updated_at": "2026-08-03T07:58:00.000Z"
      }
    ]
  }
}
```

成功响应校验：

- `code` 必须为 `0`，`data` 必须为对象，`complete` 必须为 `true`；缺失或为 `false` 时整个响应无效。
- `snapshot_id` 必须为非空字符串；`generated_at` 必须为 RFC 3339 UTC 时间，不得明显晚于 Airis
  当前时间。
- `accounts` 必须为数组，允许为空；`total` 必须是非负整数且与数组长度完全相同。
- `account_id` 必须是 `1..64` 字节非空字符串；`name` 必须是 `1..128` 字节字符串。
- 每条 `apikey` 必须是 UTF-8 编码后 `1..64` 字节字符串；同一批次内 `account_id` 和 `apikey`
  必须分别全局唯一。
- `secret` 是可直接用于验签的明文，必须是 UTF-8 编码后 `1..256` 字节；不得 trim 或截断。
- `status` 必须是整数；仅 `1` 表示启用，其他整数均按禁用账号处理。
- 每条 `updated_at` 必须是 RFC 3339 UTC 时间。Airis 的 `refreshed_at` 以本次成功接收并完整校验
  批次的本地 UTC 时间为准，不直接使用 `generated_at` 或 `updated_at`。
- 任意一条账号非法、唯一键重复或批次元数据不一致时，必须拒绝整个批次，不得部分回填。
- 目标 `apikey` 不在已完整验证的 `accounts` 中时，才视为权威 not-found；空且完整的账号数组
  表示当前没有任何账号。

Mock 的 HTTP 与业务码约定：

| 场景 | HTTP | `code` | Airis 处理 |
| --- | ---: | ---: | --- |
| 完整账号快照查询成功 | 200 | 0 | 整批校验后批量回填，再查找目标 `apikey` |
| Mock token 缺失或错误 | 401 | 40101 | 运营中心依赖错误，不重试 |
| Mock 内部错误/不可用 | 500/503 | 50001/50301 | 运营中心依赖错误，不写缓存 |
| 超时、无法解码 JSON、未知 `code` 或响应字段非法 | 不固定 | 不固定 | 非法/失败响应，不写缓存 |

为稳定验证故障路径，Mock 识别仅在测试环境开启的 `X-Mock-Scenario`：

| Header 值 | Mock 行为 |
| --- | --- |
| `server_error` | 返回 HTTP `503` + `code=50301` |
| `timeout` | 保持请求未响应，直到调用方 Context 取消 |
| `invalid_json` | 返回 HTTP `200` 和无法解析的 JSON |
| `invalid_account` | 返回 HTTP `200` + `code=0`，但其中一条账号的 `secret` 为空，用于验证整批拒绝 |
| `duplicate_apikey` | 返回 HTTP `200` + `code=0`，但两条账号的 `apikey` 相同 |
| `incomplete` | 返回 HTTP `200` + `code=0` + `complete=false` |

Mock 固定完整快照至少包含：`mock_enabled_key` -> `status=1`、`mock_disabled_key` -> `status=0`。
fixture 中的所有 Key 和 secret 都必须是专用测试值，不得从真实账号、请求日志或生产数据复制。

### 后续鉴权策略扩展

首期只实施 `apikey` 存在、`status == 1` 和账号独立 secret 验签。账号过期、并发数限制和 IP 白名单
作为已知扩展点，在业务语义和错误契约确认前不生效，也不构成本次实施的待确认项。

#### 账号过期时间

- 后续可向 `accounts` 增加 `expires_at DATETIME(3) NULL`，统一使用 UTC；`NULL` 推荐表示不限期。
- 账号快照在 Redis/L1 中携带 `expires_at`，缓存条目的过期时间不得晚于账号 `expires_at`。
- 校验使用可注入时钟；建议 `now >= expires_at` 即视为过期并拒绝，实施前需确认边界语义。

#### IP 白名单

- 使用独立 `api_account_ip_rules` 表保存账号与 IPv4/IPv6 CIDR 规则，不将多个 IP 拼接到账号表字符串或 JSON 字段。
- 账号需要显式的 `ip_whitelist_enabled` 状态，以区分“未启用白名单”和“已启用但规则为空”；
  后者建议拒绝全部请求。
- 规则解析使用 Go `net/netip`，只比较规范化 IP/CIDR，不做字符串前缀匹配。
- 必须先确认反向代理信任边界和 Gin `TrustedProxies`；不得盲信客户端可伪造的 `X-Forwarded-For`。
- IP 规则可随账号快照缓存，变更时必须清理该账号的 Redis/L1 条目。

#### 账号并发数限制

- “并发数”定义为某账号同时处理中的请求数，不是 QPS；后续可增加可空的 `max_concurrency`，
  `NULL` 推荐表示不限制。
- 多实例下必须使用 Redis 原子租约，不使用进程内计数。推荐每账号使用 ZSET，以请求唯一 ID 为 member、
  租约到期时间为 score，通过 Lua 原子执行“清理过期租约 -> 检查数量 -> 新增租约”。
- 请求结束时释放租约，租约 TTL 用于进程崩溃时最终回收；TTL 必须覆盖最大请求时长并限制上界。
- 仅当账号启用并发限制时，Redis 才是该策略的强依赖；Redis 不可用时建议 fail closed，不得默认超限放行。
- 并发租约应在 API Key/status/过期/IP/签名均通过后申请，避免无效请求占用账号并发额度。

后续完整判定顺序建议为：

```text
apikey 存在 -> status == 1 -> 未过期 -> IP 白名单
  -> 账号 secret 签名验证 -> 申请并发租约 -> 执行业务 -> 释放租约
```

上述扩展实施时必须补充边界测试：过期时刻、IPv4/IPv6/CIDR、代理头伪造、空白名单、并发临界值、
请求异常结束后的租约释放、进程崩溃后 TTL 回收和 Redis 故障时 fail-closed。

## 接口与兼容性

- 保持 `POST /loan` JSON 中 `apikey` 的位置、名称和签名参与方式不变。
- 保持现有“参数排序拼接 + `key=secret` + MD5”签名格式不变，但服务端验签密钥从全局
  `SECRET_KEY` 改为按 `apikey` 查得的账号独立 secret。这是服务端对真实契约的修正，客户端签名规则和 secret 不变。
- 空 `apikey` 继续按现有参数错误处理。
- 对于非空但不存在或已禁用的 Key，返回 HTTP `200` + `ErrInvalidApikey (2001)`；对外不区分不存在与禁用。
- 对于账号 secret 签名验证失败，返回 HTTP `200` + `ErrInvalidSign (2002)`。
- 鉴权拒绝的 JSON 响应保持 `status`/`msg`/`sid`/`data` 形状。
- L1/Redis/MySQL 故障或未命中应继续下一层；运营中心故障且没有 60 秒内的新鲜本地记录时整体 fail closed，
  不得绕过鉴权继续查询业务数据。此类系统故障返回 HTTP `503` + `ErrServiceUnavailable (9002)`，
  不返回依赖原始错误。

## 错误、超时和可靠性

- 使用 `c.Request.Context()` 传递取消，并为 Redis 和 MySQL 分别设置子超时；不复用现有 Redis 封装中的
  `context.Background()`。
- 每层统一返回 `hit` / `not_found` / `dependency_error`，不得用空字符串合并不同状态。
- L1 错误/未命中/过期继续 Redis；Redis 错误/未命中/过期继续 MySQL；MySQL 错误/未命中/过期继续运营中心。
- 运营中心批次必须先完整校验，再在一个 MySQL 事务中批量 upsert；任何记录非法时不得部分写入。
- 对已完整校验的批次，MySQL/Redis/L1 回填是 best effort；回填失败不覆盖本次从批次中得到的
  目标账号鉴权结果。
- 不在同一请求中自动重试运营中心，避免在故障时放大负载。
- 运营中心是全量批次接口；不同 Key 并发回源也应共享同一次在途刷新，请求等待必须可被 Context
  取消，避免重复下载整个账号快照。
- 账号禁用以运营中心状态变更为准。若运营中心支持变更通知，Airis 收到后删除 Redis Key 并通知各实例删除 L1；
  通知缺失或失败时按新鲜度/TTL 最终收敛，从运营中心变更成功到所有实例拒绝请求不得超过 60 秒。
- secret 轮换后同样应失效 Redis/L1，防止继续使用旧 secret 验签；是否支持主动通知不影响 60 秒最终收敛上限。
- 运营中心超时/不可用/返回非法响应，且没有新鲜本地记录时，必须按鉴权依赖错误 fail closed，
  不得降级为全局 `SECRET_KEY` 或超过 60 秒的旧账号记录。

## 安全与隐私

- MySQL 可存储明文 `apikey` 作为凭据标识，但日志、Redis Key 和 L1 Key 中不输出明文 `apikey`。
- 运营中心返回明文 secret，且现有签名验证必须使用原 secret；因此 MySQL、Redis 和 L1 会保存明文 secret。
  这是明确的安全风险，不得在评审中把它描述为密文存储。
- 运营中心、Redis 和 MySQL 连接必须使用加密传输及最小权限账号；Redis Key 设置不超过 60 秒 TTL，
  MySQL 限制表级访问。Redis/MySQL 静态加密能力尚待核实，未提供时必须记录明文 secret 持久化的残余风险。
- 运营中心认证凭据由运行环境受控注入，不得写入仓库、MySQL、Redis 或日志。
- 同步修改请求日志，删除或遮罩 `phone`、`apikey`、`sign` 和响应业务数据。这是鉴权上线前置条件。
- 只记录鉴权结果类型、内部 `account_id`、路径、业务码和耗时；不记录请求凭据。
- secret 长度、编码和生成强度以运营中心契约为准；Airis 拒绝空值、非法编码或超过 256 字节的 secret。
- 现有 MD5 签名是已知安全风险，本次为保持客户端签名格式不主动改算法；服务端签名比较应改为常量时间比较。

## 性能与可观测性

- `apikey` 唯一索引保证 MySQL 单点查询，不扫描表。
- 运营中心只在三层存储均未命中、过期或故障时调用；由于每次返回全量账号，上线前必须验证账号总量、
  响应字节数、延迟、QPS 和可用性，并为响应 Body 设置可配置硬上限。
- 上线前需在代表性数据量下测量各层命中率、p50/p95/p99 鉴权耗时、MySQL QPS 和整体吞吐，
  当前没有可验证的延迟目标，不虚构数值门槛。
- 记录按结果分类的计数和耗时：`l1_hit`、`redis_hit`、`mysql_hit`、`operation_center_batch_success`、
  `operation_center_snapshot_miss`、`operation_center_batch_size`、`key_not_found`、`account_disabled`、`stale_record`、`l1_error`、
  `redis_error`、`mysql_error`、`operation_center_error`、`cache_backfill_error`；
  只有项目接入指标系统后才升级为 metrics，首期可使用不含凭据的结构化日志。
- 异常的未知 Key 比例可作为攻击或客户端配置错误信号，但不记录 Key 本身。

## 风险、发布和回滚

### 主要风险

- 现有服务端对 API Key 只校验非空并使用全局 `SECRET_KEY` 验签，与客户端每账号独立 secret 的契约冲突；
  上线前必须用运营中心中的真实合法账号做隔离回归。
- Redis 和 MySQL 故障可继续向运营中心降级，但会增加权威源负载；运营中心故障且没有新鲜本地记录时鉴权失败。
- 缓存会使 `status` 变更存在短暂不一致，所有层的新鲜度和 TTL 必须保证禁用在 60 秒内生效。
- 随机无效 Key 可导致缓存穿透和内存污染；需要短负缓存和 L1 容量上限。
- 明文 secret 进入 Airis 内存、Redis 和 MySQL，扩大凭据泄露面；必须严格执行网络加密、最小权限、日志脱敏和存储访问审计。
- 冷启动或缓存大量同时过期时可能集中请求运营中心，需要跨 Key 批次回源合并和 TTL 缩短型抖动。
- 全量账号响应会占用网络和内存；真实账号规模超出单批可控范围时，需先调整真实接口契约，不在 Airis
  中默认接受无界响应。

### 发布顺序

1. 业务方确认运营中心账号查询契约及全部现有合法账号，不从现有请求日志导出凭据。
2. 审核 MySQL 驱动、运营中心客户端与新增环境配置；在目标环境创建 `accounts` 表和唯一索引。
3. 在隔离环境使用运营中心返回的账号记录验证 MySQL -> Redis -> L1 回填、新鲜度和脱敏。
4. 使用现有客户端的 `apikey + secret` 完成回归，不要求客端更换 secret。不得在账号查询失败时回退到全局 secret。
5. 配置独立 Redis Key 前缀、最小权限 MySQL 账号和运营中心认证凭据，验证三个依赖的超时和故障路径。
6. 发布日志脱敏、三层鉴权查询和测试；开放流量前验证各层命中、降级、禁用和 fail-closed。
7. 观察各层命中率/错误率、运营中心错误/延迟、Redis/MySQL 延迟和 `/loan` 总体延迟。

代码回滚到上一版即会恢复原有“API Key 仅校验非空 + 全局 `SECRET_KEY` 验签”行为，属于安全降级，需明确授权。
MySQL 表和 Redis Key 在回滚时保留并自然过期，
不做破坏性删除；待故障原因解决后可重新发布。

## 实施边界

- 总是执行：鉴权先于贷款数据查询；L1/Redis/MySQL 未命中、过期或异常时继续下一层；只有运营中心失败且
  没有 60 秒内的新鲜本地记录时 fail closed；不记录凭据；使用唯一索引和有界缓存；增加单元、分层降级、
  组件和契约测试。
- 先询问：修改 HTTP/业务码；新增 MySQL 驱动和运行时依赖；确定运营中心调用契约/超时/容量和身份注入；
  确定 TTL/容量/禁用 SLA；扩展角色权限；
  增加管理接口；迁移或废弃现有 Key；执行任何目标环境脚本。
- 绝不执行：在日志、响应或导出文件中记录明文 secret；鉴权依赖故障时放行或回退到全局 secret；
  运行 `cmd/init_mongo.go` 或其等价重建操作；未确认客户端兼容前修改现有签名格式。

# Mongo 初始化与取消边界：设计

## 已确认问题和目标

用户确认修复Mongo初始化持锁I/O、锁等待不能取消及Query预算建立过晚。
来源：pkg/mongo/client.go/get/close/connectMongoClientWithConfig、store.go/Query；
临时overlay探针已复现取消请求和关闭超时仍等锁，以及MONGODB_TIMEOUT不覆盖初始化。
旧测试只验证快速初始化/结果/关闭，不覆盖慢初始化期间的取消和关闭。

## 方案与依赖顺序

1. 先补行为失败测试，复用pkg/mongo既有测试文件：等待取消、首请求取消隔离、同轮失败共享、
   关闭取消初始化、迟到候选清理、关闭预算/重复等待、初始化超时与Query总预算。
2. clientManager短锁只管理closed/client/在途轮次/关闭状态。每轮独立done与有界初始化Context，
   锁外Connect+Ping；get等待选择自身Context、关闭通知、初始化完成或初始化预算耗尽。
   同轮等待者共享成功/失败结果；失败轮完成后，新请求可重试，不把失败永久缓存。
3. 独立初始化预算与MONGODB_TIMEOUT一致（非法/缺失仍回退5s）；不绑定首个请求取消。
   Query在get之前建立总Context，初始化等待和Find共享该预算及上游更早的截止时间。
4. Close先短锁标记关闭并通知等待者，再锁外取消初始化；后台等待候选完成及清理。
   不允许关闭后发布客户端；即使连接实现迟到返回成功也要独立有界Disconnect且只执行一次。
   Close调用者按自身Context等待；超时可返回，后续Close仍等待同一清理结果，不启动新关闭任务。
   已发布客户端的Disconnect也在锁外、独立5s清理Context中执行；保留清理错误供后续关闭调用获知。
5. 不通过替换mutex为另一把长锁解决；不增加依赖/包/配置，保持Mongo同包拆分及main整洁。

## 合同、错误和边界

- t/v、gzip/CSV、变量映射、查询字段、公开路径/参数/业务码不变。
- MONGODB_TIMEOUT明确包含初始化等待与Find；预算耗尽沿已有context超时映射504/9003，
  普通连接故障仍503/9002，关闭后新Query仍不可用。不把超时包装成ErrUnavailable改变映射。
- Init预算独立于等待者；所有等待者取消后，可在预算内继续完成并缓存，Store关闭会取消它。
- Connect失败/迟到成功/空客户端不得被缓存；部分候选必须清理。Ping失败已有有界Disconnect保留。
- 不承诺强制中断gzip/CSV纯CPU解码，不为本次修复增加数据大小/字段数量业务上限。
- 网络适配器须遵守Context；若适配器忽略取消，Close仍按调用预算返回，并等待迟到资源清理，
  Go不能强制杀死该goroutine。真实驱动断线恢复/TLS/容量仍需隔离环境验证。

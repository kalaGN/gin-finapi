# 限流窗口与异常日志：设计

创建日期：2026-10-15。用户确认修复最新审查第 2 项限流窗口、第 3 项 Panic 请求日志。

## 根因与目标

- ratelimit.go 使用 lastSeen 重置计数，但放行时更新 lastSeen，连续请求推迟窗口重置。
  本地模拟 200ms/2 次，0、121、242ms 请求第三次仍返回 429。
- 外层 Recovery 捕获业务 Panic 前，Logger 的 c.Next 已异常展开，跳过完成日志。
  本地模拟确认 HTTP 500 但无完成记录。

## 方案与验收

1. 采用最小按 IP 固定窗口：windowStart 为该 IP 本窗口首次放行时间，达到 window 后重置。
   lastSeen 仍用于访客清理，不再决定窗口是否到期；不增加依赖、配置、目录或分布式限流。
   固定窗口边界允许短时间相邻两窗口的突发，不宣称任意滑动区间都不超过额度。
2. 提取内部 allowLocked(ip, now) 便于确定性测试，生产 allow 在持锁后读取 time.Now；操作仍在既有锁内完成。
   覆盖连续请求、精确到期、同窗口超额、独立 IP、并发额度和既有清理/关闭行为。
3. 保留外层 Gin Recovery 保护 CORS/日志中间件；Logger 后增加同款 Recovery 保护业务处理。
   业务 Panic 被内层恢复后 Logger 正常收尾；内层已恢复的异常不会被外层重复恢复。
   CORS 预检仍提前返回，限流/认证顺序不变，不自行实现错误体或追加业务码。
4. 未写响应的业务 Panic 保持 HTTP 500 和空响应体：日志 http_status=500、status=null、success/charge=0/0。
   已写响应后 Panic 不伪造或覆盖已发 HTTP/Body；response_data、status 和 success/charge 按实际响应保持原规则。
   同请求只生成一次完成记录，不记录 Panic 原文到请求日志；既有 Gin 诊断日志行为不在本轮重构。
5. 验证异常记录通过真实文件异步后端输出，保留完整 input、毫秒时间和无顶层 msg 的约定。
   不改变 Redis RPUSH、重试两次、丢弃策略、容量预算或日志内容授权。
